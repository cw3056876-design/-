# 03 · 方案与主线

> 阶段 3 文件。回答:几种干法选哪个?主路怎么走?产出主线与方案卡——进入原型前的最小事实源。

---

## 一、方案选型(有准入条件,不是必经仪式)

**准入**:M / L 级,且方案存在真实分歧时才做对比表。方案自明的(个人中心记录页还能怎么做?)写一句"方案自明,未做对比"直接进主线。

```markdown
## 方案对比
| 方案 | 形态 | 用户价值 | 成本量级 | 主要风险 | AI 依赖 | 结论 |
|---|---|---|---|---|---|---|
| A [[ 如:拍照识别 ]] | | | 高/中/低 | | 核心/辅助/无 | 选用/备选/排除 |
| B [[ 如:手动录入优化 ]] | | | | | | |

选用理由:[[ 一句话 ]] (状态:AI 建议 / 待确认 / 已确认)
```

- "AI 方案 vs 规则方案 vs 人工方案"的取舍在这里做:规则能解决就别用 AI,AI 是成本不是荣誉。
- 选了 AI 依赖的方案,对应节点立即按 02 挂`待验证`;若预验证已有结论(如`需人工兜底`),方案设计必须体现兜底环节。
- 成本量级只写 高/中/低 + 一句依据,拿不准就标`待技术确认`——这里是选方向,不是排期。

## 二、功能主线卡模板

`需求-[[需求名]]/主线与方案卡.md`(方案对比与主线卡同文件)

```markdown
## 功能主线卡
| 模块 | 内容 | 状态 |
|---|---|---|
| 功能目的 | 为什么存在,解决什么问题 | |
| 目标用户 | 谁在什么场景用 | |
| 触发入口 | 从哪进 | |
| P0 主线 | 3-7 步,只写主路径 | |
| 主线终点 | 完成后用户看到 / 得到什么 | |
| 成功标准 | 见下方写法要求 | |
| 本版不做 | 明确排除的范围 | |
| AI / 规则 / 人工边界 | 哪些 AI 做、哪些规则做、哪里必须人工确认(含预验证结论要求的兜底) | |
| 待确认问题 | 会影响主线 / 规则 / 范围的问题 | |
| 本卡状态 | 草稿 / 待确认 / 已确认(带证据:谁/何时/依据) | |
```

**成功标准的写法要求**:必须可观测——写"上线 30 天识别功能使用率 ≥X%、识别确认率 ≥Y%"这类能埋点验证的表述,不许写"体验更好"。这一格是阶段 5 埋点章和阶段 7 回流单的源头,写不出可观测标准,说明还没想清楚要验证什么。

## 三、硬闸

- [ ] M/L 级且有分歧的需求,方案对比表存在;自明的已声明。
- [ ] 主线卡十格填齐,P0 主线 3-7 步。
- [ ] 成功标准可观测。
- [ ] AI 依赖方案的节点已挂`待验证`,或已有预验证结论且兜底进了边界格。
- [ ] 主线卡状态为`已确认`(带证据)方可作为事实源;未确认时,下游原型一律`演示假设`。

---

## 四、常见错误

| 错误 | 修正 |
|---|---|
| 给自明方案硬凑三个对比项 | 一句"方案自明"带过,别表演 |
| 成功标准写"更高级、更流畅" | 改成可埋点观测的表述 |
| 选了 AI 方案却没挂预验证 | 回 02 挂节点,状态`待验证` |
| 主线卡没确认就当事实源写 PRD | 主线卡状态与证据栏是阶段 5 的入场券 |
