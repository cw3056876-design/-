# 06 · 构建交接(可选)

> 仅当用户明确要交给 Cursor / Claude Code / v0 / 工程团队时生成。没有构建意图,链路停在规则集,直接说"06 暂不需要"。本阶段只转译,不新增产品决策。

---

## 一、入场券

- 明确构建意图(原型构建 / 工程落地 / 现有代码改造,三选一写明)。
- 规则集(主事实源)+ PRD(背景参考,不搬长文)+ 已确认原型。
- 技术选型:不明确时先问用户,用户允许占位才出 Draft,且不得标"可开工"。落地到现有工程的,必须拿到框架 / 目录 / 依赖约束。

---

## 二、构建包模板

`需求-[[需求名]]/构建包.md`

```markdown
# [[需求名]] · 构建包

## 0. 来源与状态
来源规则集 / PRD / 原型;构建意图;状态:Draft / Ready for Build / Blocked。
上游`待确认`项分级:阻塞构建 / 不阻塞但影响上线(只能 mock 占位) / 后续版本。
> 阻塞项克制使用:只有缺了无法开工、无法验收、或会把待确认能力做成正式能力的才算。

## 1. 技术选型与运行方式
| 项 | 选择 | 已确认? |
|---|---|---|
| 前端框架 / 语言 / 样式 / 状态管理 | | |
| 数据存储 | localStorage / mock / API | |
| AI 调用方式 | mock / 后端代理 | |
| 运行方式 | 双击 HTML / npm run dev / 部署 | |

## 2. 命名与实体模型
产品名词 → 工程命名;实体字段表(mock 也要写,标注"mock 数据",不替代正式 DB schema)。

## 3. 页面与路由构建表
| PAGE-ID | 路由/呈现 | 读写实体 | 验收方式 |

## 4. 交互与流程实现表
| FLOW-ID / ACT-ID | 触发 | 系统动作 | 状态变化 | 失败兜底 | 验收方式 |

## 5. 规则实现表
| RULE-ID | 输入字段 | 判定逻辑 | 输出 | 测试用例(输入→预期输出) |
> 每条关键规则必须有测试用例,没有就是不可验收。

## 6. AI 节点实现表
| AI-ID | 实现方式(mock/真实调用) | 输入输出 | 规则约束 | 人工确认 | 失败回退 | 禁区 | 起点 prompt |
|---|---|---|---|---|---|---|---|
> 起点 prompt = 评测集里的实测基线(含通过率),不许从零编。预验证结论为`需人工兜底`的节点,人工确认环节必须实现,不可省略。

## 7. 状态、异常与兜底实现表

## 8. 合规红线
| 红线 | 植入位置(具体 FLOW/ACT/AI) | 验收方式 |

## 9. 构建任务拆解
顺序:骨架 → 实体 → 页面路由 → P0 流程 → 业务规则 → AI 节点 → 异常兜底 → 红线 → 验收。每步写输入、输出、依赖。

## 10. 验收矩阵
覆盖:P0 页面可开、主流程可点通、规则可验证(跑测试用例)、AI 边界可验证、异常可触发。

## 11. 开工指令
"严格按第 9 章顺序执行,不新增产品需求,不把待确认项实现为正式能力,遇阻塞先停并列出问题。"
```

---

## 三、硬闸

- [ ] 有明确构建意图,不是默认生成。
- [ ] 技术选型无影响开工的`待确认`,否则状态只能 Draft / Blocked。
- [ ] 待确认项已分级;演示占位与假设没被做成正式能力。
- [ ] 每个 AI 节点带实测基线 prompt 与人工确认实现要求。
- [ ] 关键规则都有测试用例;红线有植入位置;P0 有验收项。
- [ ] 没有重新定义产品需求。

---

## 四、常见错误

| 错误 | 修正 |
|---|---|
| 没有构建意图就生成 06 | 停在规则集,说明缺什么 |
| 把待确认 AI 能力做成真实调用 | 改 mock / 占位 / 阻塞 |
| 工程从零写 prompt | 移交评测集里的实测基线 |
| 验收矩阵只有 happy path | 补异常态与红线验收 |
